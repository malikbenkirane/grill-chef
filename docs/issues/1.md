# State database & session storage

## Context

The grill-chef MCP server must survive crashes, tool timeouts, and multi-day idle stalls. All state is owned server-side and persisted to disk so any grill-chef process can rehydrate any session from its id alone.

Referenced in grill rounds: R1 (Q1.1 create-and-wait, server owns all state), R2 (Q2.1 global state on disk), R2 (Q2.2 wild stalls for hours/days).

## Requirements

- Store location: `os.UserCacheDir() + "/grill-chef/state.db"`.
- Must be readable and writable by any grill-chef process (stateless handlers over a global cache).
- Track **sessions**: id (server-minted), name (human-readable, from `grill_start`), created_at, status (`active` | `closed`).
- Track **rounds** per session: round number (1..5), round payload JSON (intro, recap branches, questions), submitted answers per question, round status (`pending` | `submitted`).
- Track **daemon metadata**: pid and port of the HTTP listener, so recovery tooling can health-check and respawn.
- Concurrency-safe: multiple agents may call MCP tools simultaneously, each touching different sessions; the store must not corrupt under concurrent access.
- Go stdlib only for the store implementation (encoding/json, os, sync). No external database dependency.

## Dependencies

None — this is the foundation for all other issues.

## Acceptance criteria

- Can create a session, store rounds, store answers, and retrieve the full session state by id.
- Daemon metadata (pid + port) persists across process restarts.
- Concurrent writes to different sessions do not corrupt.
- A stale session (no submitted answers after hours/days) is fully recoverable from its id alone.
