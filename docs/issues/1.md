# State database & session storage

## Context

The grill-chef MCP server must survive crashes, tool timeouts, and multi-day idle stalls. All state is owned server-side and persisted to disk so any grill-chef process can rehydrate any session from its id alone.

Referenced in grill rounds: R1 (Q1.1 create-and-wait, server owns all state), R2 (Q2.1 global state on disk), R2 (Q2.2 wild stalls for hours/days).

## Requirements

> Note (issue 3 grilling): session statuses are the domain's
> `Active | Closed` (rendered as `active | closed` at the store edge).
> Daemon state (pid/port) is stored alongside, as adapter data — never
> as part of session semantics.

- Store engine: SQLite, accessed through `github.com/glebarez/go-sqlite` (pure-Go driver, no cgo — preserves the single-binary distribution promise).
- Migrations: `github.com/pressly/goose/v3` in library mode — Go-code migrations with `init()` registration, embedded via `//go:embed`, applied idempotently at startup through `goose.NewProvider(goose.DialectSQLite3, db, fsys)` + `provider.Up(ctx)`. No CLI at runtime. Both processes migrate with `goose.WithSessionLocker(...)`.
- Store location: `os.UserCacheDir() + "/grill-chef/state.db"`.
- **Dual-writer topology**: two processes touch the file, each through its own sqlite connection, with disjoint row ownership:

| Table | Writer | Notes |
|-------|--------|-------|
| sessions, questions | MCP (stdio) process | agent-facing tool calls create/mutate these |
| answers, comments | web daemon | browser autosave / submit / comment routes |
| rounds | both, by column | MCP writes payload columns; daemon owns `status` |

  WAL journal mode and `busy_timeout` set in the setup DDL are mandatory for this topology. Ownership is enforced at the type level: the store's Go surface is a domain aggregate (one method per write path, see below), so each writer's methods only exist for rows it owns.
- **Schema** — five tables: `sessions`, `rounds`, `questions`, `answers`, `comments` (comments are first-class, matching the per-comment DELETE route in issue 8). FK spine on `session_id`; composite indexes on `(session_id, round)` and `(session_id, round, question)`. Full session rehydration is a single indexed read — no post-load merge in Go.
- Track **sessions**: id (server-minted), name (human-readable, from `grill_start`), created_at, status (`active` | `closed` | `dismissed`). `closed` is set when the round payload of a legend `grill_round` call is processed — not by round counting. `dismissed` is set when the human clears the session from the station home (issue 14); retention policy is keep-everything — dismiss is a status change, never a delete.
- Track **rounds** per session: round number (1..5), round payload (intro, recap branches, questions), submitted answers per question via the `answers` table, round status (`pending` | `submitted`, daemon-owned).
- Track **answers** per question: defined by (session, round, question); autosave is the hot path, so answers live in their own table rather than payload JSON blobs. Comments are separate rows with their own ownership.
- **Daemon metadata** (pid + port of the HTTP listener) lives in a marker file `os.UserCacheDir() + "/grill-chef/daemon.json"`, rewritten by the listener on bind — the database stays a pure session store, and recovery tooling + the human-only `stop` CLI read the file without touching the db or its WAL sidecars.
- **Consistency check**: `IsSessionConsistent(id)` — gap-based (round numbers contiguous 1..N with no voids; every `pending` round has its full question set). This is the correctness check consumed by `grill_recover` (issue 4). `updated_at` columns are a separate staleness commodity, not part of the correctness check.
- **Persistence design**: hexagonal — domain layer connects through an interface at `internal/port/store`, with the SQLite adapter under `internal/port/store/sqlite`. Exported aggregate-store methods express the ownership matrix above; no domain code writes SQL directly.
- Concurrency-safe under the two-writer topology above; the store must not corrupt when an agent tool call and a browser autosave race.

## Dependencies

None — this is the foundation for all other issues.

## Acceptance criteria

- Can create a session, store rounds, store answers, and retrieve the full session state by id.
- Daemon metadata (pid + port) persists across process restarts.
- Concurrent writes to different sessions do not corrupt.
- A stale session (no submitted answers after hours/days) is fully recoverable from its id alone.
