# Issue 7 — Daemon HTTP listener lifecycle

## Context

The HTTP server that renders browser pages must outlive the MCP client process.
It starts lazily when `grill_start` first needs it, detaches as a daemon child,
and records its pid + port in the state database. The user never manually
starts or stops it (except via the CLI `stop` subcommand). Recovery tooling
health-checks via pid and respawns if stale.

Referenced in grill rounds: R2 (Q2.1 HTTP server starts if not already
started), R3 (Q3.1 listener outlives MCP client, detached daemon), R4 (Q4.1
detached daemon child, pid+port in state, health-check and respawn), R5
(Q5.1 agent cannot stop, CLI-only stop).

## Requirements

- The HTTP listener starts as a detached daemon child process, fully
  decoupled from the MCP stdio client process.
- On startup:
  1. Bind a dynamic port (ephemeral range, e.g., 49152-65535).
  2. Write pid + port to the state database (issue 1).
  3. Detach from the parent (double-fork or equivalent Go daemonization).
- On `grill_start` or `grill_recover` (issues 4, 6):
  1. Read pid + port from state.
  2. Health-check: is the pid alive and listening on the port?
  3. If alive: reuse the existing daemon, do nothing.
  4. If stale or absent: spawn a new detached daemon.
- **Agent cannot stop**: no MCP tool exposes a stop/restart capability. The
  agent's only lifecycle interaction is idempotent re-start (respawn on
  stale pid). An explicit "no stop tool" clause goes into the skill prose
  (issue 15).
- **Human CLI stop**: `grill-chef stop` subcommand kills the daemon by its
  recorded pid. This is a terminal command, never an MCP tool.
- **Human CLI web**: `grill-chef web` subcommand manually starts the daemon
  (for development/testing).
- Multiple processes: if a second process tries to bind while the first is
  alive, it detects the existing daemon via the state db pid+port health
  check and exits its HTTP part (no double-bind).

## Dependencies

- Issue 1 (state database — daemon metadata storage)

## Acceptance criteria

- After `grill_start`, the daemon is running and its pid+port are in state.
- If the daemon is killed, `grill_start` or `grill_recover` respawns it.
- The MCP client can exit and restart; the daemon keeps running.
- `grill-chef stop` (CLI) kills the daemon; `grill-chef web` (CLI) starts it.
- No MCP tool can stop or kill the daemon.
- Two concurrent `grill_start` calls do not spawn two daemons.
