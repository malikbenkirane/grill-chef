# MCP tool: grill_round

## Context

The core tool that drives a grill round. The agent sends the current round's JSON payload, the server stores it in state and renders the screens. The tool call **blocks** (long-running) until the user submits the round in the browser (screen E). On submit, the server returns the round's answers as the tool result. Grill stations can stall for hours or days; the cached state (issue 1) plus `grill_recover` (issue 6) handle timeouts and stalls.

Referenced in grill rounds: R1 (Q1.1 create-and-wait, tool blocks until submit), R2 (Q2.2 stalled grills recoverable), R3 (Q3.3 drive_round sends current round only, screens render from state), R4 (Q4.2 tool naming).

## Requirements

> Note (issue 3 grilling): answers carried by `grill_round` return as a
> `round.AnswerSheet` aligned with the questions (1-based choices, skip =
> `ChoiceIndexNone`, other = `ChoiceIndexOther` + >= 1 comment). Product
> caps (5 questions / 5 options) are enforced here, in the tool — not in
> the domain. There is no round cap: frontier closure terminates the
> session.

- Tool name: `grill_round`.
- Input parameters:
  - `session_id` (string, required): the session id from `grill_start`.
  - `payload` (object, required): the round JSON (issue 3 schema). For the final round, may instead carry a `legend` payload.
- Behavior on round payload:
  1. Validate the session exists and is `active` in state (issue 1).
  2. Store the round payload in state (issue 1) under the session's round number.
  3. The server renders the round's screens from state (issue 8): intro recap, question screens, recap/submit screen.
  4. **Block** the tool call until the user submits the round via the browser (screen E).
  5. On submit, mark the round as `submitted` in state, freeze answers as immutable, and return the round result (issue 3 schema) as the tool result.
- Behavior on legend payload (final round, optional):
  1. Store the legend in state.
  2. Render the legend screen (issue 13).
  3. Return immediately (no blocking — the legend is informational).
- Blocking durability:
  - Emit MCP progress/keepalive notifications to prevent client-side timeouts where the SDK supports them.
  - If the tool call times out or disconnects, the session and round remain intact in state. The agent can call `grill_recover` (issue 6) to resume.
- Round caps enforced: 5 questions max, 5 options max per question, up to 5 rounds per session. The server should reject payloads exceeding caps.

## Dependencies

- Issue #1 (state database — round storage)
- Issue #2 (session identity — session_id parameter)
- Issue #3 (JSON schema — payload and result shapes)
- Issue #4 (grill_start — session must exist)
- Issue #8 (HTML routes — screens must render for the user to submit)

## Acceptance criteria

- Calling `grill_round` with a valid round payload stores it in state and renders the round screens in the browser.
- The tool call blocks until the user submits; on submit, returns the answers as the result schema (issue 3).
- If the tool times out, the session and round remain intact in state.
- A legend payload renders the legend screen and returns immediately.
- Payloads exceeding caps (6+ questions, 6+ options) are rejected with an error.
- Answers are immutable after submit (a second `grill_round` for the same round number returns an error).
