# EPIC 1 — MCP Server & State Infrastructure

## Scope

Everything agent-facing: the durable state store, session identity, the JSON
payload contract, the three MCP tools (`grill_start`, `grill_round`,
`grill_recover`), and the detached HTTP daemon lifecycle. This EPIC delivers
the complete MCP surface that the agent interacts with.

## Execution order

1. **Issues 1 and 3** (parallel, no deps): state database foundation and JSON
   schema design spec.
2. **Issue 2** (after 1): session identity on top of the state store.
3. **Issue 7** (after 1): daemon HTTP listener detached lifecycle.
4. **Issue 4** (after 1, 2, 7): `grill_start` tool — first MCP tool, creates
   sessions and ensures the daemon is running.
5. **Issue 8** (EPIC 2, after 1, 2, 3, 7): HTML routes — cross-EPIC dependency;
   `grill_round` cannot block-and-wait until the user can see and submit
   screens.
6. **Issue 5** (after 1, 2, 3, 4, 8): `grill_round` tool — the blocking call
   that drives a round and returns answers on submit.
7. **Issue 6** (after 4, 5, 7): `grill_recover` tool — recovery path for
   stalled sessions.

## Cross-EPIC dependencies

- **Issue 5 depends on EPIC 2 issue 8** (HTML routes): `grill_round` blocks
  until the user submits via the browser; the routes must exist for
  submission to work.
- **EPIC 2 issue 11 depends on EPIC 1 issue 5**: the recap/submit screen
  unblocks `grill_round` on submit; the submit endpoint calls into the same
  state and unblock mechanism.

## Key decisions

- Go single binary, stdlib only (official MCP SDK accepted), stdlib templates.
- State: `os.UserCacheDir()/grill-chef/state.db`, stdlib JSON store,
  concurrency-safe.
- Transport: MCP over stdio; HTTP daemon is a detached child.
- Tools: namespace-prefixed verb-first (`grill_start`, `grill_round`,
  `grill_recover`).
- Agent cannot stop the server; CLI-only `grill-chef stop`.
- Create-and-wait: `grill_round` blocks until submit; stalls recover via
  `grill_recover`.
- No full transcript echo in tool results; agent owns history.
